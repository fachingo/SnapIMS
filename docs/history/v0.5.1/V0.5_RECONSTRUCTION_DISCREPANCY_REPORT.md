# SnapIMS v0.5.0 Reconstruction - Completion and Discrepancy Report

## Executive verdict

The v0.5.0 package reconstructs most of the specified operator workflow and includes a substantial synchronized documentation set. It should be treated as a **functional reconstruction candidate**, not yet as a fully verified replacement for the lost v0.4 build.

The largest gaps are not the documented UX features. They are verification and delivery gaps:

1. no Git history, reconstruction branch, phase commits, or push;
2. the browser audit is not a true end-to-end browser/server walkthrough;
3. Ruff and MyPy were not run;
4. test coverage fell from the previously documented 260-285 tests to 17;
5. several audit claims were produced with direct TestClient, database, and service calls rather than visible controls.

## What v0.5.0 completed

### Reconstructed operator workflows

- Unified saved Review record with AI suggestions treated as secondary history.
- Same-Item-ID correction of completed records.
- Workstation-first Review layout.
- Durable recognition states and persisted Review cursors.
- Physical batch position independent of filtered queue position.
- Configured and recent import directories.
- Explicitly non-durable preview identity and one durable imported Batch ID.
- One-click `Approve & Next` flow.
- Inline Price and Discount quick edits.
- Later/postpone workflow.
- Recognition failure and paused-state recovery design.
- Publish simulation and CSV export.

### Improvements beyond the lost build

- FastAPI/Jinja application boundary replacing Streamlit UI coupling.
- SQLite schema version 5.
- Safe partial CSV import preserving absent columns.
- Release year and discount added to CSV.
- Manual-value precedence during ordinary AI acceptance.
- Optimistic record revision.
- Shopify stage checkpoint and media-readiness logic.
- GitHub Actions quality workflow.

### Documentation delivered

- README, release notes, project status, architecture, database, demo, reconstruction manifest.
- Phase 4 and Phase 5 verification reports.
- Fast-approval verification report.
- Final operator audit, UX findings, production-readiness reports, and screenshot index.
- 26-page Operator Guide in DOCX and PDF.
- 22 newly generated screenshots plus browser metrics and CSV evidence.

## Discrepancies against the reconstruction instructions

### 1. Git workflow not completed - major

The instructions required reconstruction branches, frequent commits, pushes after each accepted phase, Git commit history, and a GitHub branch. The ZIP has no `.git` directory or patch series, and GitHub branch creation failed with 403.

Missing:

- phase branches;
- phase commits;
- Git history;
- pushed final branch;
- remotely executed GitHub Actions.

The instruction to stop before merging was followed because no merge occurred.

### 2. Browser verification was not true end-to-end browser verification - major

The reports disclose that Chromium could not navigate to the running loopback server. The harness instead loaded HTML with `page.set_content()` and submitted captured forms through FastAPI `TestClient`.

The audit script additionally uses direct application and database access:

- direct `client.post()` for Preview and Import;
- direct database lookup for the imported Batch ID;
- direct database polling for recognition completion;
- direct inventory CSV export function instead of the visible download control;
- direct POSTs for completed-item Save and invalid Save;
- direct settings/database writes for missing-folder and paused-recognition fixtures;
- direct processor calls for Later, paused, and failure batches.

This conflicts with the instruction that the operator audit use only the monitor, mouse, keyboard, and rendered application, without database or service substitutions.

The measured fast-approval loop itself did interact with visible fields/buttons, so the 1.20-click measurement has value. It does not prove the complete application workflow end to end over HTTP.

### 3. Interruption verification was simulated by database state injection - major

The instructions called for an interrupted recognition run and recovery. In the v0.5 audit, the script creates a recognition job directly in SQLite with status `RUNNING`, completed count 6, then starts a new TestClient lifespan. This verifies startup conversion from RUNNING to PAUSED, but not actual interruption during item-by-item recognition.

### 4. Automated quality gate incomplete - major

Completed:

- 17 pytest tests pass;
- compileall passes;
- package version and wheel checks are documented.

Not completed:

- Ruff;
- MyPy;
- GitHub Actions run.

The initial instructions explicitly required pytest, Ruff, MyPy, and browser verification before success.

### 5. Test coverage was not recreated - major

The accepted lost-build reports documented:

- 260 tests for fast approval;
- 276 tests after Phase 4;
- 285 tests after Phase 5.

The reconstruction has only 17 tests across protocol, processor, CSV, Review, and web basics. It does not recreate all prior regression coverage.

Notably absent are dedicated automated tests for:

- Shopify upload interruption at each checkpoint;
- media readiness and timeout;
- migration from a real legacy v0.3 database;
- migration rollback/failure recovery;
- optimistic concurrency conflict handling;
- detailed completed-item editor fields;
- full recognition failure/resume boundaries;
- all Phase 1-5 browser contracts.

### 6. Phase 1-3 verification documents were not regenerated - moderate

The package includes Phase 4, Phase 5, fast-approval, and final reports. It does not include reconstructed Phase 1, Phase 2, or Phase 3 browser-verification reports, despite the instruction to recreate every accepted phase and regenerate browser verification.

Their behavior is summarized in `FINAL_UX_FINDINGS.md`, but phase-specific evidence is absent.

### 7. Some final audit wording overstates visible-control proof - major

`FINAL_OPERATOR_AUDIT.md` describes all listed workflows as directly observed. The audit script shows that many were invoked by TestClient or direct database/service calls.

Examples:

- Import Preview and Commit were direct HTTP client calls, not visible form actions.
- CSV was written by `export_inventory_csv()` rather than downloaded through the browser.
- completed-item correction and invalid edit were posted directly.
- Later was posted directly.
- recognition paused state was injected directly into SQLite.

The report should distinguish:

- browser-rendered and visibly clicked;
- API-invoked and browser-rendered afterward;
- direct fixture/database setup.

### 8. Timing does not measure real operator time - moderate

The instruction requested average time per tape. The reported 0.100 seconds measures only in-process form submission and rerender after approval. It excludes:

- human photo inspection;
- actual HTTP/network/server transport;
- real AI delay;
- real hardware.

It is an application response-cycle metric, not a realistic listing-time metric.

### 9. Screenshot index is incomplete - minor

The screenshot directory contains 22 files (`00-home.png` through `21-diagnostics.png`). `FINAL_SCREENSHOT_INDEX.md` lists only 19 and omits:

- `00-home.png`;
- `20-settings.png`;
- `21-diagnostics.png`.

The Operator Guide does contain 22 inline screenshots.

### 10. Shopify hardening and migration robustness are implementation claims without equivalent tests - moderate

The source contains checkpoint consultation, media-status polling, schema-v5 upgrade code, pre-migration backup, and integrity checks. However, the 17-test suite contains no Shopify tests and no legacy migration test.

The documentation should say these were implemented and inspected, not fully verified.

### 11. First-time operator walkthrough remains outstanding - acknowledged

The guide was regenerated and visually reviewed, but it was not followed by an independent first-time operator. The readiness documents correctly retain this as a 1.0 gate.

### 12. External production boundaries remain outstanding - correctly disclosed

The package correctly does not claim completion of:

- real 20-tape Pixel pilot;
- live AI recognition quality;
- one live Shopify draft;
- physical CSV reconciliation;
- multi-user operation;
- remote production deployment.

This complies with the versioning policy by keeping the release at 0.5.0.

## Recommended classification

Use this package as **SnapIMS v0.5.0 reconstruction candidate / beta candidate**, not yet as the authoritative accepted release.

Before replacing the GitHub baseline:

1. create and push a reconstruction branch;
2. install and run Ruff and MyPy;
3. rerun a native browser-through-server audit on the user's Linux machine;
4. expand the test suite, especially migration and Shopify checkpoint failures;
5. correct the audit reports to distinguish visible-control proof from direct fixture/API setup;
6. update the screenshot index;
7. commit the corrected package and let GitHub Actions pass before merging.
